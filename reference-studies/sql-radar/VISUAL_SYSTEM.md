## 2. Two-layer experience

The creator explicitly divides the report into:
- Native visuals for data and interactions.
- HTML for the experience.

This separation suggests that the analytical structure and interaction model are intended to remain native, while HTML supplies the distinctive map, timeline animation, identity cards and introduction.

## 3. Mercury and Glitch

The assistant changes persona with the report's light/dark state:
- Mercury: light mode, a drop of liquid metal.
- Glitch: dark mode, a pixel bug from SQL logs.

The creator says both provide the same insights, but Glitch has a more playful tone.

This is a distinctive narrative device. The exact visual design, animation and interaction are not available from the source description.

## 4. Status hierarchy

The Signal page makes three values explicit for each system:
- Threshold.
- Headroom.
- Drift status.

This is an important visual hierarchy because it communicates both current proximity to a limit and movement away from normal.

The source does not provide the exact colour palette, status colours, pill shape or label style.

## 5. Visual inspection checklist

When the PBIX or screenshot becomes accessible, verify:
- Whether threshold, headroom and drift status can be understood at a glance.
- Whether the map and selected-system state remain synchronised.
- Whether animated timelines make deviations clearer or create distraction.
- Whether the diagnosis table distinguishes new, explained and shared changes.
- Whether the criticality-versus-signal matrix has clear axes and labels.
- Whether the runway timeline communicates time and priority clearly.
- Whether the action plan is visually separate from the analysis.
- Whether Mercury/Glitch state changes preserve status-colour meaning.
- Whether the assistant is keyboard accessible and its answers are traceable.
